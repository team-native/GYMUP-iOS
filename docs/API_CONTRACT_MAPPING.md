# API contract mapping

Source of truth: [GYMUP V1 - API 기명서](https://held-space-801.notion.site/74a03c3f306b8340af6b8173d381f661?v=93703c3f306b82e6b84d0895f7f570b7&source=copy_link).

The Notion table contains 38 endpoint rows. This document keeps the request/response contract and an app-callsite map for all 38 rows. All GYMUP API calls use `Authorization: Bearer <JWT>` with `USER` access. Fields follow the Notion contract unless a limitation is stated below; server errors retain the `{detail:{code,message}}` envelope for UI mapping.

## Networking foundation scope

`APIEnvironment(baseURL:)`, `APIEnvironmentConfiguration`, and `APIServiceContainer` provide the networking foundation and centralize API client/service construction. Debug builds read `GYMUP_API_BASE_URL` from `Config/Info-Debug.plist`, explicitly set to `http://localhost:8000`. The generated Release Info.plist exposes the same key, supplied by the `GYMUP_API_BASE_URL` build setting (for example, an Xcode Release configuration or `xcodebuild ... GYMUP_API_BASE_URL=https://api.example.com`); there is no localhost fallback. `APIEnvironmentConfiguration` rejects a missing or invalid value, so container creation fails safely.

`BearerTokenProviding` is injectable into `APIServiceContainer`, but this repository has no production implementation. `DevelopmentBearerTokenProvider` is compiled only in Debug builds. The app therefore does not create API services or send API requests in Release until a production token provider is added and injected. The configured Release base URL alone does not enable requests.

For the workout photo route, the client requests upload metadata after the user saves the rendered workout photo to Photos, then sends the image bytes with a `PUT` to the returned storage URL using only the server-provided `uploadHeaders`. The signed storage request does not use the app's Bearer token. Failed storage uploads can retry the same URL while it remains valid; retrying does not create another metadata record. The app currently has no production bearer token provider, so API services remain unavailable in Release builds until one is added and injected.

Photo filter and stamp requests are submitted after the original image uploads. Their `202 PROCESSING` job responses contain no result data, and the Notion table has no job-status or job-result route. The app keeps the locally rendered filter/stamp output for Photos and sharing, and does not present the server job as completed. Timed exercises remain local-only because the workout set request has no duration/seconds field.

Routine editing sends exercise additions, field updates, removals, and an absolute exercise order through the two documented routes above. Exercise writes include only fields accepted by the backend. The editor's routine title remains locally editable; neither route accepts a name update, so the title is not sent to the server and the existing server routine name remains unchanged.

An exercise `PATCH` can have an ambiguous outcome if the server applies it but the response is lost. The iOS editor keeps the exact request for retry and uses the server's returned exercise state before attempting a separate order `PUT`. Safe retry of an ambiguous `add` depends on the approved paired backend hardening: repeated items must be idempotent by `exerciseId`, updating their fields without changing their current order. The absolute order `PUT` remains authoritative. This iOS change does not add an idempotency header or alter the request shape.

The routine playlist screen reads Apple Music library playlists or Spotify playlists with read-only access, then sends the selected provider's metadata (`provider`, `playlistId`, `playlistName`, `externalUrl`) to the GYMUP playlist `PUT`. If a local routine has no `serverRoutineId`, the app uses the existing routine-create flow first; it never sends a local/sample routine ID. Since the 38-route table has no routine-list or playlist-read route, a successful `PUT` is stored in the local `RoutineStore`; the app cannot refresh that playlist relationship from the server on another device or after local data is cleared.

The goal-completion request requires `expectedVersion`. The Notion contract names the field but does not document its initial value. The current backend implementation creates goals with version `1` and does not mutate a goal version before completion; the progress and weekly-goal read responses omit version. The app sends `expectedVersion: 1` based on that backend implementation evidence, not a Notion-stated rule. Revisit this mapping if the backend adds another goal mutator or exposes version in a response.

The avatar-items response contract types `items` only as an opaque JSON array, without item fields the app can map into its barbell inventory model. The app requests `status=all`, `size=20`; the current backend implementation returns an empty array, shown as an empty inventory. A nonempty response currently reports the count and that item detail is not yet displayable. `/avatar` uses level, growth, stage, and weekly goal in existing Home/Growth UI; `modelKey`, `morphValue`, and `equippedItems` are decoded but have no corresponding model/asset mapping in the current UI. The workout reward response replaces displayed XP and shows growth delta; unknown bonus payload shapes remain opaque.

Apple Music access uses `MusicAuthorization` and `MusicLibraryRequest<Playlist>` for read-only library listing. `NSAppleMusicUsageDescription` is configured in the app Info.plist, but the MusicKit App Service must also be enabled for App ID `com.teamnative.gymup` in Certificates, Identifiers & Profiles and reflected in the signing setup. The project does not add a fabricated MusicKit entitlement; Apple associates the MusicKit App Service with the bundle ID at runtime. Spotify uses Authorization Code with PKCE and requests only `playlist-read-private`; access and refresh tokens are stored in Keychain. The registered redirect URI must exactly match `com.teamnative.gymup.spotify://oauth/callback`; the URL scheme is registered in the app, but a Spotify Client ID must be supplied through the `GYMUP_SPOTIFY_CLIENT_ID` build setting and the matching redirect must be registered in Spotify Developer Dashboard. No client secret is embedded in the app. The GYMUP playlist request stores only `apple_music` or `spotify` and selected playlist metadata.

The callsite map is a static source review. No GYMUP server response, Docker run, build, or test was performed as part of this API wiring change.
